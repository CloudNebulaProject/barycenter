# Admin GraphQL API

Barycenter exposes an administration API on a dedicated port, separate from the public-facing OIDC endpoints. By default, the admin API listens on the main server port plus one (e.g., if the OIDC server runs on port 8080, the admin API runs on port 8081). This separation allows operators to restrict admin access at the network level using firewalls, Kubernetes NetworkPolicies, or reverse proxy rules without affecting public OIDC traffic.

## Two GraphQL Schemas

The admin API serves two independent GraphQL schemas, each at its own endpoint:

| Endpoint | Playground | Purpose |
|---|---|---|
| `POST /admin/graphql` | `GET /admin/playground` | Generated [Seaography schema](./entity-crud.md); entity reads unavailable |
| `POST /admin/jobs` | `GET /admin/jobs/playground` | [Job management](./job-management.md), [user 2FA management](./user-2fa.md), and client trust |

### Entity CRUD Schema (`/admin/graphql`)

This schema is auto-generated by Seaography from Barycenter's SeaORM entities.
Its generated resolvers are not connected to the database, so entity reads are
unavailable. The generated types contain credential columns and must not be
enabled on the unauthenticated admin listener. Use the hand-written queries at
`/admin/jobs` for client metadata and trust.

See [Generated Entity Schema](./entity-crud.md) for the current limitations.

### Job and User Management Schema (`/admin/jobs`)

This schema provides custom queries and mutations for operational tasks that go beyond simple CRUD:

- **Trigger background jobs** on demand (e.g., force a cleanup cycle without waiting for the next scheduled run).
- **Query job execution logs** with filtering by job name and failure status.
- **List available jobs** and their schedules.
- **Inspect client metadata and trust** through secret-free `client` and `clients` queries.
- **Manage user 2FA settings** (enable/disable 2FA requirements, query enrollment status).

See [Job Management](./job-management.md) and [User 2FA Management](./user-2fa.md) for details.

## Client Trust

The custom schema at `POST /admin/jobs` exposes:

```graphql
# Query
client(clientId: String!): ClientGql
clients: [ClientGql!]!

# Mutation
setClientTrusted(clientId: String!, trusted: Boolean!): ClientGql!
```

For example, after registering Sokar, use its actual client ID:

```graphql
mutation {
  setClientTrusted(clientId: "SOKAR_CLIENT_ID", trusted: true) {
    clientId
    clientName
    redirectUris
    trusted
  }
}
```

Set `trusted: false` to restore normal consent checks. The mutation returns safe
client metadata without the secret, or a GraphQL error with code
`barycenter::client::not_found` and recovery help if the client is absent.
The `client` and `clients` queries return the same secret-free type. An unknown
client ID returns `null`; listing clients returns an array (empty when none are
registered). `clientSecret` is not a field of `ClientGql`, and requesting it fails
GraphQL validation.

```graphql
query {
  client(clientId: "SOKAR_CLIENT_ID") {
    clientId
    clientName
    redirectUris
    trusted
  }
  clients {
    clientId
    trusted
  }
}
```

These operations use the existing admin port's network/proxy access model. The
GraphQL listener has no built-in authentication layer; restrict it to authorized
operators. These queries and mutations are not mounted on the public OIDC service.

Alternatively, with access to the configured database:

```bash
barycenter --config /path/to/config.toml client trust SOKAR_CLIENT_ID
barycenter --config /path/to/config.toml client trust SOKAR_CLIENT_ID --untrust
```

The CLI exits nonzero for a missing client. Trust skips interactive consent only;
login and 2FA remain required, `prompt=consent` forces consent, and `prompt=none`
retains its existing session and prior-grant checks. See
[Consent Flow](../authentication/consent.md#trusted-first-party-clients) for
implicit grants and revocation semantics.

## Accessing the Admin API

The admin API is intended for operators and automation tooling, not end users. Access it using any GraphQL client, `curl`, or the built-in GraphQL playgrounds.

### Using curl

```bash
# Safe client metadata
curl -s -X POST http://localhost:8081/admin/jobs \
  -H "Content-Type: application/json" \
  -d '{"query": "{ clients { clientId clientName redirectUris trusted } }"}'

# Job management: list available jobs
curl -s -X POST http://localhost:8081/admin/jobs \
  -H "Content-Type: application/json" \
  -d '{"query": "{ availableJobs { name description schedule } }"}'
```

### Using the Playground

Open the appropriate playground URL in a browser for interactive query building:

- **Generated entity schema playground (reads unavailable)**: `http://localhost:8081/admin/playground`
- **Job management playground**: `http://localhost:8081/admin/jobs/playground`

See [GraphQL Playground](./playground.md) for more on using the playground interface.

## Configuration

The admin API port is derived from the main server configuration. If you set the main port via the configuration file or environment variable, the admin port adjusts accordingly:

```toml
[server]
port = 9090
# Admin API will be available on port 9091
```

Or via environment variable:

```bash
export BARYCENTER__SERVER__PORT=9090
# Admin API will be available on port 9091
```

## Security Considerations

The admin GraphQL listener has no built-in authentication layer and exposes
operational controls. Generated entity reads remain unavailable; hand-written
client queries omit credentials. In production deployments:

- **Do not expose the admin port to the public internet.** Bind it to a loopback or internal network interface, or use firewall rules to restrict access.
- **Use a reverse proxy** with authentication if remote admin access is required.
- **In Kubernetes**, use a separate `Service` for the admin port and restrict access with `NetworkPolicy` resources.
